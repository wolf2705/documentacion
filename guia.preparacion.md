# Temas para revisar para FullStack

> requiero hacer assesments para full stack con C# y angular
> sabes como puedo hacerlo?

Sí. Si necesitas crear **assessments técnicos para Full Stack .NET/C# + Angular**, puedo ayudarte a diseñarlos desde cero.

## Areas a revisar

Te recomiendo que el assessment evalúe **4 áreas**:

### 1\. C# / .NET

- C# moderno: LINQ, async/await, generics, interfaces
- OOP y SOLID
- Dependency Injection
- ASP.NET Core Web API
- Entity Framework Core
- Manejo de errores y validaciones
- Authentication/Authorization con JWT
- Unit testing

### 2\. Angular

- Components
- Services e Injection
- RxJS / Observables
- Routing
- Reactive Forms
- HTTP Client
- Guards / interceptors
- Manejo de estado
- Performance
- Unit testing

### 3\. Full Stack

Aquí es donde puedes diferenciar un candidato realmente bueno.

Por ejemplo, pedirle construir:

> **Product Management API + Angular UI**

El candidato tendría que:

- Crear una API REST en ASP.NET Core.
- Usar EF Core con SQL Server.
- Implementar CRUD de productos.
- Agregar búsqueda, filtros y paginación.
- Implementar autenticación JWT.
- Crear la aplicación Angular.
- Consumir la API mediante un service.
- Crear formulario de alta/edición.
- Manejar errores y loading states.
- Escribir tests.
- Documentar cómo ejecutar el proyecto.

### 4\. Preguntas de entrevista

## Preguntas en general

Además del coding assessment, puedes tener preguntas como:

**C#**

- ¿Cuál es la diferencia entre `IEnumerable`, `IQueryable` y `List`?
- ¿Qué problema resuelve Dependency Injection?
- ¿Cuándo utilizarías `async/await`?
- ¿Qué es `CancellationToken`?
- ¿Cómo evitarías un N+1 query con EF Core?

  **Angular**

- ¿Cuál es la diferencia entre Observable y Promise?
- ¿Cuándo usarías `Subject` o `BehaviorSubject`?
- ¿Qué hace un HTTP interceptor?
- ¿Cómo manejarías un formulario complejo?
- ¿Cómo optimizarías una aplicación Angular con muchos componentes?

  **Architecture**

- ¿Cómo estructurarías una aplicación ASP.NET Core + Angular?
- ¿Dónde colocarías las validaciones?
- ¿Cómo manejarías errores entre API y frontend?
- ¿Cómo implementarías autorización por roles?
- ¿Qué harías para evitar que un usuario modifique recursos que no le pertenecen?

## Una estructura que funciona muy bien

Yo haría **3 niveles**:

| Nivel     | Duración  | Objetivo                            |
| --------- | --------- | ----------------------------------- |
| Junior    | 60–90 min | Fundamentos C# + Angular            |
| Mid-level | 2–3 h     | API + Angular + DB                  |
| Senior    | 3–5 h     | Full stack + arquitectura + testing |

Y no evaluaría solamente si "funciona". Le pondría una rúbrica, por ejemplo:

- **C# / .NET:** 25%
- **Angular:** 20%
- **Database / EF Core:** 15%
- **Architecture:** 15%
- **Testing:** 10%
- **Code quality:** 10%
- **Documentation:** 5%

### Así puedes comparar objetivamente a varios candidatos.

Si quieres, puedo prepararte **un assessment completo listo para enviar a candidatos**, incluyendo **el enunciado, repositorio inicial sugerido, requisitos funcionales, bonus points, preguntas de entrevista y una rúbrica de evaluación de 100 puntos**, específicamente para **C#/.NET + Angular**.

var result = await context.Users

## 42\. Decisión final

La evaluación debería considerar tres dimensiones:

```csharp {.line-numbers}
                    CANDIDATO
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
       Código       Arquitectura    Defensa
          │             │             │
          └─────────────┼─────────────┘
                        ▼
                 DECISIÓN FINAL
```

Un candidato Senior debe demostrar las tres.

Un código perfecto técnicamente pero que el candidato no puede explicar debe generar dudas.

Del mismo modo, una excelente conversación arquitectónica no compensa completamente una implementación deficiente.

La combinación de:

```csharp {.line-numbers}
            Código
              +
         Arquitectura
              +
    Experiencia práctica
              +
    Capacidad de diagnóstico
              +
     Comunicación técnica
```

es la que debería determinar la decisión final.

#### Una diferencia importante respecto al Mid

Para **Mid** yo pondría el peso en _"¿puede construir correctamente una feature?"_.

Para **Senior**, esta prueba pregunta además:

> **"¿Puede construirla de forma que sobreviva a concurrencia, fallos, crecimiento y cambios futuros?"**

Y hay cuatro puntos que yo **no negociaría para un Senior Full Stack**: **concurrencia de inventario, idempotencia, diseño de API y capacidad de explicar trade-offs**. Si falla fuertemente en esos cuatro, aunque el CRUD funcione muy bien, no lo consideraría Senior.
